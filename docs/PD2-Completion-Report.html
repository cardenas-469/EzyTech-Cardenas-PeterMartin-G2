1. Project Overview

EzyTech is a Django + PostgreSQL e-commerce platform for technology products. Project Development 1 delivered the account and role features. Project Development 2 adds the approved core feature — Product Catalog & Order Management — as a complete vertical slice from the database to the user interface.

Users can browse products, place orders, and track them. Administrators manage the catalog and process customer orders. All feature records are stored in PostgreSQL/Supabase.

2.2 Core Feature (PD2) — Product Catalog & Order Management

Database layer

  • Product: name, description, price, stock, created_by (ForeignKey to User), created timestamp.
  • Order: user (ForeignKey to User), product (ForeignKey to Product, PROTECT), quantity, total price, status, created timestamp.
  • Relationships follow the ERD: one user has many orders; one product appears in many orders.
  • Migrations are committed and applied to PostgreSQL/Supabase.

Status flow: Pending → Confirmed → Shipped → Completed. Pending and Confirmed orders may be cancelled. Cancelled and Completed are terminal states.

Backend layer

  • Product list with search, product create, update, and delete.
  • Checkout with server-side validation, stock deduction, and order creation.
  • Order history with status filtering and search, plus a dedicated order detail page.
  • Order cancellation, order deletion, and admin-controlled status updates.
  • Django views, ModelForms, and URL routes for every operation.

Frontend layer

  • Django templates for catalog, product form, delete confirmation, checkout, order history, order detail, and status update.
  • Clear success and error messages for every action.
  • Role-aware navigation bar and dashboard links.

2.4 Validation and Business Rules

  • Quantity must be at least 1 and cannot exceed available stock.
  • Price must be greater than zero; product name has a minimum length; stock cannot be negative.
  • Checkout runs inside transaction.atomic() with select_for_update() to prevent overselling under concurrent requests.
  • Cancelling or deleting an active order restores stock exactly once.
  • Cancelled orders already have their stock restored; completed sales keep their stock deduction.
  • Products with order history cannot be deleted, preserving transaction records.
  • Invalid order status transitions are rejected.

2.5 Account Integration and Role-Based Access

  • Every feature page requires login.
  • Orders are linked to the logged-in user through Order.user.
  • Customers only see and manage their own orders; attempts to access another customer's order are rejected.
  • Only admins can create, edit, or delete products and change order statuses.
  • Feature links appear on the correct role dashboard; admin-only links are hidden from customers.

6. Outstanding Issues

  • Supabase's connection pooler does not support the CREATE DATABASE statement used by Django's test runner. manage.py test therefore automatically switches to an in-memory SQLite database, while the application itself reads and writes PostgreSQL/Supabase. An explicit config.settings_test module is also provided. This is documented in the README.
  • The optional sample_products fixture creates seed data without a created_by user because it is system-provided. Products created through the admin UI are correctly linked to the admin who created them.
  • Checkout is single-product per order, matching the approved scope. A multi-item cart is future work.
  • Development test accounts must be rotated or removed before public deployment.
